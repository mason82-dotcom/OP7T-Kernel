# V0lk3n NetHunter kernel source variant (experimental; no flash)

## Decision and scope

On this **isolated branch**, `KERNEL_VARIANT=v0lk3n` selects the pinned [V0lk3n SM8150 source](https://github.com/V0lk3n/nethunter_kernel_oneplus_sm8150/tree/nethunter-lineage-23.2) instead of the experimental KernelSU Next source. **No KernelSU patch, driver symlink, hook, manager or privileged userspace is injected.** The normal `main` default remains the official crDroid kernel. The old KernelSU draft PR #33 remains preserved solely for traceability; it is **not** included in this variant.

Exact source ref: `nethunter-lineage-23.2` at commit `d5dee6f73a667dcfa978288be7053dce08127948` (4.14.357 family). V0lk3n targets **LineageOS 23.2 / Android 16**, whereas this project targets **crDroid 13 / Android 17** on OnePlus 7T Pro `hotdog`. Lineage compatibility is not evidence of crDroid compatibility.

Relevant references:
- [Kali NetHunter kernel registry](https://nethunter.kali.org/kernels)
- [V0lk3n kernel README](https://github.com/V0lk3n/nethunter_kernel_oneplus_sm8150/blob/nethunter-lineage-23.2/README.md)
- [Independently tested hotdog LOS 23.2 / Android 16 guide](https://github.com/althsec/nethunter-oneplus7tpro-los23.2), **not** crDroid 13 evidence
- [Our release blockers](FLASHING.md), [physical/reference evidence](HARDWARE_EVIDENCE.md)

## Critical compatibility caveats

1. Previous experimental KernelSU Next source built at observed crDroid SHA `57037290bb57` but had **185 mismatched CRCs out of 394 imported WLAN symbols**, **`-dirty` vermagic**, and a different module-signing key compared with the reference OTA's `qca_cld3_wlan.ko`. Replacing the source does not automatically fix those problems.
2. The V0lk3n source's `arch/arm64/configs/vendor/oplus.config` explicitly contains `# CONFIG_MODULE_SIG is not set`. We must **not** carry this downgrade into our target. This branch merges the `v0lk3n-security.fragment` last, enforcing `CONFIG_MODULE_SIG=y`, `CONFIG_MODULE_SIG_FORCE=y`, automatic signing and an autogenerated **build-only** key. If Kconfig rejects this, **stop**, do not bypass the check.
3. The live crDroid kernel's original trusted module-signing certificate is not available. Rebuilt modules' own CMS signatures can validate internally but do not prove installed ROM key trust; mixing signed original and rebuilt modules is unsafe until proven.
4. The V0lk3n source's configuration and submodules are materially different (external WLAN/CAN modules and Kali builder). The `nethunter/nethunter_defconfig` serves as a candidate baseline, with the OPlus config and strict signing overlay applied. No USB/monitor/injection feature is claimed to work on crDroid.
5. **Root is not installed by this switch.** The documented working LineageOS configuration used Magisk as a separate component. Never confuse NetHunter kernel features with successful `su` root or KernelSU.
6. No `boot.img`, dtbo, AVB, OTA repack, partition write, runtime key-trust claim, bypass, or flash action is implemented.

## Use on Raspberry Pi 5 (source-only)

```bash
git fetch origin feature/hotdog-v0lk3n-nethunter-source
git worktree add --detach ../OP7T-Kernel-V0lk3n-Review origin/feature/hotdog-v0lk3n-nethunter-source
cd ../OP7T-Kernel-V0lk3n-Review
bash scripts/fetch-v0lk3n.sh
python3 -m unittest discover -s tests -q
```

This fetch clones into `.work/v0lk3n-kernel`, not `.work/kernel` or `.work/kernel-ksu`. Use `--submodules` only when intentionally preparing to compile. The Pi ARM64 is **not** supported by the project's x86_64 build path.

## Experimental build on Linux x86_64 / WSL2 ext4

```bash
# In THIS branch/worktree, with the toolchain from docs/BUILD.md:
export KERNEL_VARIANT=v0lk3n
CONFIG_ONLY=1 bash scripts/build.sh baseline
# Only if CONFIG_ONLY passes and upstream submodules/toolchain are reviewed:
bash scripts/build.sh baseline
```

The alternate work directories are `.work/out-v0lk3n-baseline` and `.work/artifacts/v0lk3n-baseline`; the crDroid and KernelSU artifacts remain intact. The build will intentionally **fail closed** if forced signed modules, Kconfig or existing module artifact gates cannot be satisfied.

For CI, explicitly select `variant=v0lk3n` with `profile=baseline` from a manual workflow_dispatch in this branch. Pull requests perform lint and unit testing but do **not** automatically build an unsupported cross-ROM kernel.

## First compiled-build result and tightly scoped preflight (2026-10-25)

Manual CI run [40222874008](https://github.com/mason82-dotcom/OP7T-Kernel/actions/runs/40222874008) **FAILED** in actual compilation, despite successful lint, Clang14 installation and accepted forced module signing:

- DTS: `arch/arm64/boot/dts/18821/pm8150.dtsi:21` parse error during the 18821 `sm8150-mtp-overlay.dtbo` target.
- WLAN: `wlan_hdd_frame_inject.h` could not be found when compiling `wlan_hdd_assoc.o`; it exists under `drivers/staging/qcacld-3.0/core/hdd/inc`. The Kbuild defines `HDD_INC`, but the `INCS` sequence omitted it.

The new, limited `patches/v0lk3n-build-compile-preflight.patch` **attempts** to insert an empty DTS root before included fragments and adds `$(HDD_INC)` to the WLAN include search path. `scripts/prepare-v0lk3n-build.sh` applies the patch only when the source is at the pinned commit with a completely clean worktree; `git apply --check` and a strict two-file modification list must succeed, otherwise the build stops. This does not validate the resulting Device Tree, firmware, feature functionality, ABI or module-signing trust.

The patch is applied **inside the ignored experimental source checkout**, not in the original V0lk3n GitHub repository. The resulting checkout is deliberately modified and the build may acquire a `-dirty` kernel suffix. The patch digest is recorded in `v0lk3n-source-patch.sha256`. The compile-path hypothesis is **unproven until a new manual CI build**. The source checkout is not designed for repeated builds after patch application without recreating a clean checkout; fail-closed behavior is intentional.

### Second compilation attempt: new specific failures

Manual [run 40225953270](https://github.com/mason82-dotcom/OP7T-Kernel/actions/runs/40225953270) compiled past the initial `wlan_hdd_frame_inject.h` error, proving the `$(HDD_INC)` search path addresses that missing header. It then failed at `wma_frame_inject.h`, a header actually present under `drivers/staging/qcacld-3.0/core/wma/inc`. The new revision also adds the already-defined `$(WMA_INC)` to QCACLD's `INCS` variable; compilation of that path is not yet independently confirmed.

The attempted empty top-level DTS root removed the previous parser-syntax error, but the build instead failed on *many* unresolved external DT labels (`soc`, `tlmm`, `snd_9360`, etc.). The V0lk3n `scripts/Makefile.lib` compilation rule lacks `-@`, which Android's overlay compilation documentation requires for symbol/fixup generation. The new revision adds conditional `DTC_FLAGS += -@` when `CONFIG_BUILD_ARM64_DT_OVERLAY=y`, retaining the empty root. This is a **testable build hypothesis**, not proof that the resulting DTBO loads correctly, corresponds to `hotdog`, or applies to the installed reference base tree. The source patch now modifies **three** files, strictly checked by the preflight script.

The full kernel compile with these two additional adjustments is **not yet run**. Preserve a failure-closed state if unknown headers, DTO fixups, Kconfig or signature checks fail. See original issue #3.

### Third compilation attempt: DTC parser root cause

Manual V0lk3n build [40229728199](https://github.com/mason82-dotcom/OP7T-Kernel/actions/runs/40229728199) **FAILED**. The previous QCACLD header errors were resolved, and the build reached the `LD [M] drivers/staging/qcacld-3.0/wlan.o` step, which is positive **compile/link evidence only**, not evidence that a usable, ABI-compatible or signed `wlan.ko` exists.

The 18821 `sm8150-mtp-overlay.dtbo` still fails with dozens of unknown label references, despite an explicit `DTC_FLAGS += -@`. The pinned Linux 4.14 kernel's **own** `scripts/dtc/dtc-parser.y` is the root cause: its `devicetree DT_REF nodedef` production reports unknown external references unconditionally and has no `add_orphan_node` fallback for `DTSF_PLUGIN`. These are parser errors; `-@` alone cannot solve them.

A new fix attempts to select the separate Ubuntu `device-tree-compiler` binary via the kernel's existing `DTC_EXT` switch for the V0lk3n candidate only. Before cloning or building, `scripts/check-v0lk3n-dtc.sh` compiles a minimal `/plugin/;` fixture using an unresolved target label and requires an actual `/__fixups__` record through `fdtget`. Kbuild is passed `DTC_EXT` explicitly and external DTC path, version and SHA256 are archived as `external-dtc-toolchain.txt`. **This is not yet a successful build or a validation of actual hotdog base/overlay pairing.**

The in-tree DTC remains unchanged. The previously reviewed V0lk3n source patch still affects three bounded files; neither module signing enforcement nor RTL/WLAN gates are bypassed. Any incompatible real DTS/DTBO, build failure, module trust, ABI mismatch or firmware mismatch must remain a blocker. The ability to create an overlay fixup does not prove that it resolves against the installed ROM, so `flash_ready=false` remains mandatory.

### Fourth compilation attempt: MODPOST unexported symbol

Manual [run 40232818349](https://github.com/mason82-dotcom/OP7T-Kernel/actions/runs/40232818349) **FAILED** late at `MODPOST 8 modules`: `ERROR: "get_task_cred" [drivers/staging/qcacld-3.0/wlan.ko] undefined!`. The external DTC preflight passed; real DTS compilation and `vmlinux` linking progressed, the `arch/arm64/boot/Image` target was generated inside transient CI output, and QCACLD `wlan.o` linked. None of those intermediary files passed full module/signing/ABI gates or was uploaded as a release-ready artifact. MODPOST also warned of four section mismatches requiring separate analysis.

Root cause was verified from the pinned sources: `kernel/cred.c` defines `get_task_cred()` but does not export it to modules; the QCACLD `core/hdd/src/wlan_hdd_inject_security.c` unconditionally references it when checking frame-injection privileges. The retrieved credential object was not actually used for authorization: `capable(CAP_NET_RAW)` checked the *current* process. Calling this function with a noncurrent task could therefore misleadingly authorize on the wrong caller.

The **fourth** path added to the strictly reviewed source patch removes the unexported credential getter/reference-counting code, rejects noncurrent task arguments and preserves `capable(CAP_NET_RAW)` with explicit permission-denied return. It does **not** export `get_task_cred`, relax capabilities, disable forced module signatures or change Kconfig. The fix remains an untested full-build hypothesis. There is a separate security concern in the pinned upstream `hdd_validate_injection_permissions()`: process-context capability checks are skipped in interrupt/softirq contexts. This needs independent security and call-path review; **do not treat frame injection or kernel images as ready for deployment merely because MODPOST passes**.

## Required before any hardware attempt

Prove exact installed ROM partition provenance; inspect V0lk3n-versus-original `Image`, DTBs, modules, `Module.symvers`, `vermagic`, CRC, signing trust, firmware; reproduce the original boot layout/AVB and document recovery for both slots. Unless each independent gate passes, maintain `flash_ready=false`.

**No flashing, root deployment, AVB modification, SELinux or module-signature enforcement downgrade.**
